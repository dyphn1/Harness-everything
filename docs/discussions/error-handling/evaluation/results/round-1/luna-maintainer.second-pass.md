# Second pass — differences from the blind first pass

## My reading

**Correction to my first-pass inference:** A–G are drawing-local aliases, not persistent cross-view identifiers. The README and nodes.yaml assign each Action its own persistent identifier; the drawings use letters and names for readability. The README says the seven Action IDs remain the only proposed persistent identities and are not regenerated by redrawing.

## Diagram-to-diagram mapping

The README defines three separate views: View 1 explains the overall activity, View 2 the composition, and View 3 the working detail of one Action. The repeated ASSESS and RESPOND regions, and the D expansion marker, are decomposition cues that help correlate the views. They are not clickable links, custom graph edges, or dependencies. The links between nodes in the flowcharts represent the pictured control flow; the recurrence path is conceptual and is not an automatic additional review round.

## Unclear or potentially misleading

- **Action fields:** identifier supplies persistent identity; its ERR-category/date/UUIDv4 form is immutable once accepted, while the category and date are descriptive and UUID supplies collision resistance. name is the human- and agent-readable meaning shown in the diagrams and can change independently. status is separate lifecycle metadata; all seven records currently say proposed, and the lifecycle transitions are not specified.
- **Rename or move:** For the same Action, preserve its identifier through a rename or a change in diagram region. Update its displayed name consistently when renamed. The region is a visual grouping and does not create another identity. The sources do not specify any status transition caused by a rename or move; status is separate metadata.
- **Files:** Neither the diagrams nor the README imply that a file already exists for each Action. nodes.yaml is a discussion prototype with records, and the README explicitly says this draft changes no implementation. It points to activity.puml as the corresponding PlantUML activity source, but the packet did not ask me to inspect that file.
- **Visual versus physical links:** Cross-view references and dotted associations are explanatory visual conventions. In particular, the dotted links to Reviewer / Owner, Error Ledger #359, and bounded context delivery #394 describe authority or reuse; they do not define physical connections, new graph edge types, or new mechanisms. The README says those mechanisms remain established and are not implemented by this draft.

## What I could not determine

The prototype does not define final identifier/status lifecycle rules. It also does not say how status changes should be handled after a rename or region move. These are not answered by the diagrams or the two second-pass sources.

## Confidence 0–5 with reasons

**5/5 for the differences above.** The README directly explains the view conventions and field roles, and nodes.yaml shows the seven current records and their proposed status. I did not inspect implementation files, so this is not a claim about runtime behavior.
