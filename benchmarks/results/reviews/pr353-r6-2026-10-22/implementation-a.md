## Design choices

### P1 — the captured origin identity must be the snapshot identity

`validateSnapshot()` now calls `originBound(snapshot)` (new, pure):

1. `originContext.{workspaceId,sessionId,workflowId,workflowRevision,taskId}` must equal
   `identity.{...}` — the five fields of the origin-correlated identity.
2. The captured plan must agree with that identity: `taskSemantics.workflow.{workflowId,
   workflowRevision,sessionId}`, `taskSemantics.task.taskId`, `taskSemantics.prdRoot`,
   `taskSemantics.configDigest`.
3. The captured `originContext.activeHost` must equal the host the captured config was selected for
   (`config.capture.activeHost`); the comparison is skipped only when neither side represents a host.

This closes the disconnect: events compare provider↔captured origin context and event identity↔
`snapshot.identity`, so binding the captured origin context to the identity connects the two halves. A
joint substitution of the captured origin context and the provider context now yields
`identity-mismatch` in **both** `verification` and `review` mode, in the fresh-acceptance path and in the
cached-acceptance path (the cached acceptance is re-validated against the snapshot on every core call, so
it cannot bypass the invariant).

Adjacent link closed in the same class: `configBytesBound()` requires the captured config source bytes to
be the bytes the captured inventory holds for the same path — the producer's own rule
(`doc-reconciliation-producer.js`), which the core previously did not re-check. A substituted config
digest is `config-capture-mismatch`.

### P2 — a whole-project inventory may contain binary records

* Stored bytes are untouched: every record's bytes stay in the `candidateDigest`/`baselineDigest`
  framing, so a changed binary asset changes `candidateDigest`.
* Semantic derivation needs decoded text. A record whose bytes are not valid UTF-8 is **omitted** from
  derivation only when the derive contract cannot observe it, and **fails closed**
  (`inventory-unsupported`) when it can.
* Relevance is taken from the derive contract's own surface, not from a binary-extension allowlist:
  the configured `governed`/`legacy` globs, the `derived` output/source globs, the derive contract's
  code-extension and REQ-test path rules (`doc-obligations.js` `CODE_EXTENSION`, `TEST_PATH`), plus any
  record that opens a frontmatter block (the derive contract reads the frontmatter of every captured
  file and treats a frontmatter `role` as governed).
* Producer and core re-derivation share one implementation (`_internals.deriveFiles`), so both handle
  binary records identically.
* The lifecycle reader, its byte-conversion rule (`workingStoredBytes`: a NUL byte means no text
  conversion) and the producer's explicit `MAX_FILES`/`MAX_BYTES` budgets were not altered; no public
  lifecycle helper behavior changed.

## Remaining risks

1. The relevance rules mirror the derive contract's path rules inside the reconciliation module, because
   `doc-obligations.js` is outside this write-set. A future change to the derive contract's code/test
   path rules or glob semantics must be mirrored here. The duplication is two regexes plus the glob
   semantics; the behaviour is pinned by the new tests.
2. A record whose first line is exactly `---` fails closed even when it is an irrelevant binary asset.
   This is deliberate (the derive contract observes such a file's frontmatter) but can turn an exotic
   binary asset into `inventory-unsupported`.
3. In the core, a relevant undecodable record is reported as `inventory-unsupported` and the decision is
   `unresolved` (not `unavailable`). Credit is withheld either way; the reason code differs from the
   producer's `state: "unavailable"`.
4. The producer's whole-project walk still traverses `node_modules` and is bounded by the pre-existing
   `MAX_FILES`/`MAX_BYTES` limits. That is unchanged pre-existing behavior and out of scope here.
5. Evidence is deterministic mechanism evidence only: the origin provider is an explicit test fake, so
   nothing here proves live-host provenance, reviewer independence in deployment, host loading or E1
   readiness.
